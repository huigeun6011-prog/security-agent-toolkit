## 2단계 · ping

### 문제 2-1 · 결과 화면 읽기

- 보냄 · 받음 · 손실 · 평균: 4회 · 3회 · 1회(25%) · 47ms
- 손실 % 는 보낸 수와 받은 수로 어떻게 계산했나요?
  - 답: (보낸 횟수 − 받은 횟수) ÷ 보낸 횟수 × 100으로 계산했다. 예시는 (4 − 3) ÷ 4 × 100 = 25%다.

### 문제 2-2 · 구글 DNS 서버에 `ping` 열 번 보내기

- `8.8.8.8` 까지 평균 왕복 시간 · TTL · 받음 · 손실: 35ms · 응답 10개의 TTL은 모두 115 · 10회 받음 · 손실 0%

### 문제 2-3 · 이름으로 `ping` 보내기

- `google.com` 의 IP 주소: `142.250.197.238`
- 이름만 입력했는데 IP 주소가 나온 이유는 무엇인가요?
  - 답: PC가 이름 해석을 통해 `google.com`에 대응하는 IP를 얻고, 그 주소로 `ping`을 보냈다.

### 문제 2-4 · 두 가지 실패를 구별하기

- 두 실패 문구: `abc.nowhere-not-exist`는 `Ping request could not find host ...`. `192.0.2.1`은 `Request timed out.`이 4회 표시됐다(손실 100%).
- 두 실패는 각각 어디에서 멈춘 것인가요?
  - 답: 첫 번째는 이름을 IP로 바꾸지 못해 해당 호스트에 ICMP 요청을 보낼 수 없었다. 두 번째는 숫자 IP로 요청을 시도했지만 제한 시간 안에 응답을 받지 못했다. 이 결과만으로 어디서 응답이 막혔는지는 알 수 없다.

### 찾아본 것

- 2.1 표에서 찾아 쓴 TTL 의 뜻과 라우터를 지날 때 바뀌는 방식: TTL은 패킷이 라우터를 지날 때마다 1씩 줄어드는 값이다. `ping`에 표시되는 TTL은 돌아온 응답에 남은 값이므로 초기값을 모르면 홉 수를 계산할 수 없다.

### 이 단계에 새로 안 것

- 이 단계에서 새로 알게 된 것: 구글 공개 DNS 주소에 `ping`이 된다고 해서 내 PC의 DNS 조회나 웹 접속까지 확인된 것은 아니다. 이름 조회 실패와 응답 시간 초과는 서로 다른 단서다.

## 3단계 · IP 와 MAC

### 문제 3-1 · 결과 화면 읽기

- 예시 화면의 IPv4 주소 · MAC 주소 · 기본 게이트웨이: `192.168.0.15` · `A4-B1-C2-D3-E4-F5` · `192.168.0.1`

### 문제 3-2 · 내 IP 주소 · 게이트웨이 · MAC 주소 찾기

- 찾은 장치 이름 · 내 IPv4 주소 · 기본 게이트웨이 · MAC 주소(물리적 주소): 이더넷 3 · PC IPv4 `192.168.x.x/16` · 기본 게이트웨이 `192.168.x.x` · MAC은 `물리적 주소` 항목에서 확인(공개본에서 가림)

### 문제 3-3 · 게이트웨이까지 `ping`

- 게이트웨이까지 평균 · 2-2 의 `8.8.8.8` 평균: 게이트웨이 1ms 미만(출력 평균 `0ms`, 응답별 `time<1ms`) · `8.8.8.8` 평균 `35ms`
- 게이트웨이까지가 더 짧은 이유는 무엇인가요?
  - 답: 게이트웨이는 같은 로컬 네트워크의 다음 홉이라 내부 경로만 왕복한다. `8.8.8.8`은 외부 경로까지 왕복하므로 이번 측정에서는 더 오래 걸렸다.

### 문제 3-4 · ARP 캐시 보기 — `arp -a`

- 게이트웨이 줄의 MAC 주소 · 유형: 게이트웨이 MAC은 공개본에서 가림 · 유형 `dynamic`
- 🔍 ARP 는 무엇을 알아내려고 쓰나요? 내 결과의 게이트웨이 줄을 예로 들어 설명합니다.
  - 답: 같은 로컬 네트워크에서 IPv4 주소에 대응하는 MAC 주소를 알아낼 때 ARP를 쓴다. 게이트웨이 IP의 `dynamic` 줄에 대응하는 MAC이 있었다. 이 MAC은 외부로 보내는 첫 프레임의 목적지이고, 그 안의 목적지 IP는 `8.8.8.8`이다.

### 이 단계에 새로 안 것

- 이 단계에서 새로 알게 된 것: 외부 IP로 통신하더라도 로컬 ARP 캐시에는 외부 서버가 아닌 다음 홉인 게이트웨이의 MAC이 나타났다.

## 4단계 · 포트

### 문제 4-1 · 직접 실행해 보기

- 출력 두 줄: 첫째 줄 `HTTPS` · 둘째 줄 `모름`
- `3389` 는 사전에 없는데도 에러 없이 둘째 줄이 나온 이유는 무엇인가요?
  - 답: `dict.get(3389, "모름")`은 `3389` 키가 없으면 지정한 기본값 `모름`을 돌려주기 때문이다.

### 문제 4-2 · 지금의 연결과 그 프로그램 — `netstat -ano`

- 고른 줄의 외부 포트 → 서비스 이름 · PID → 프로그램 이름: 외부 `443` → HTTPS 기본 포트 · PID `24972` → `ChatGPT.exe` (`tasklist` 확인)

### 문제 4-3 · 내 PC 의 LISTENING 포트 찾기

- 4.1 표에 있는 LISTENING 포트 → 서비스 이름: TCP `135` → RPC · TCP `445` → SMB
- 🔍 LISTENING 과 ESTABLISHED 는 무엇이 다른가요? 4-2 와 4-3 에서 본 줄을 예로 들어 설명합니다.
  - 답: 135번과 445번은 `LISTENING`이어서 연결 요청을 기다리고 있었다. 외부 443번으로 향한 줄은 `ESTABLISHED` 상태여서 TCP 연결이 맺어진 상태였다. 이 줄만으로 TLS나 웹 응답의 성공까지는 판단할 수 없다.

### 문제 4-4 · 증상으로 층 좁히기

- 증상 ① · ② · ③ 에서 의심되는 층: ① 7층의 이름 해석(DNS) · ② 로컬 네트워크의 1~3층부터 · ③ 4층 이상
- 증상마다 그렇게 판단한 근거는 무엇인가요?
  - 답: ① 숫자 IP로 통신은 되므로 이름을 IP로 바꾸는 경로를 먼저 확인한다. ② 같은 망의 게이트웨이부터 응답이 없으므로 링크, 주소 설정, 게이트웨이 상태와 ICMP 차단 여부를 점검한다. ③ IP 응답은 오므로 해당 사이트의 TCP 포트, TLS, HTTP 응답 순으로 확인한다.

### 찾아본 것

- 4.1 표에서 찾아 쓴 3389 의 위험과 445 를 이용해 퍼진 랜섬웨어: RDP(3389)를 인터넷에 노출하면 무단 원격 접속 시도의 대상이 될 수 있다. WannaCry(워너크라이)는 SMB(445)의 취약점을 이용해 확산됐다.

### 이 단계에 새로 안 것

- 이 단계에서 새로 알게 된 것: `netstat`의 외부 포트로 서비스 후보를, PID로 실제 연결을 연 프로그램을 확인할 수 있었다. `LISTENING` 상태만으로 인터넷에서 접속할 수 있는지는 알 수 없다.
